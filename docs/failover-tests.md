# 障害試験の記録

> 最終更新: 2026-11-17　データ: [monitoring/status/tests.json](../monitoring/status/tests.json)（自作の状態画面もこのファイルを読んで表示する）

本番と同じ機器を実際に止め、計測スクリプト [failtest.sh](../monitoring/status/failtest.sh) で 0.5 秒ごとに通信を確認して、次の時間を秒で記録しています。通知の時刻は Alertmanager の API（2秒ごと）や Prometheus に残ったアラートの記録から取っています。

| 用語 | 意味 |
|---|---|
| T0 | 障害を起こした瞬間（スクリプトで Enter を押した時刻） |
| 停止時間 | 利用者から見て使えなかった時間（通信が途切れてから戻るまで） |
| 検知時間 | T0 から管理者に通知（Discord）が届くまで |
| 復旧まで | T0 から通信が戻るまで |
| 目標 | 試験の前に自分で決めた合格ライン |

> 検知時間が停止時間より長いのは、自動で直った場合です。利用者への影響はすでに終わっていて、通知は「壊れた機器を直してください」という管理者向けの知らせです。一瞬の乱れで誤報を出さないよう、通知は一定時間続いてから出します。

<a id="router"></a>
### ルーター障害（#1 の電源を抜く）（✅ 合格）

- **目的**：メインのルーターが壊れても、予備の #2 が自動で引き継いでインターネットが使えるか
- **計測方法**：failtest.sh（ping 0.5秒ごと）、Prometheus に残ったアラートの発生時刻（ALERTS）
- **実施日**：2026-11-16 20:51

**試験方法**

1. 前提：#1 が担当（Master）、#2 が待機（Backup）。この画面で「#1 が担当」になっていること
2. mon01 で ./failtest.sh ping:1.1.1.1 VrrpFailover を起動する
3. Enter を押した直後に IX #1 の電源ケーブルを抜く（T0）
4. ping が戻り、Discord に通知が来るまで待つ（スクリプトが自動で終わる）
5. #1 の電源を戻し、#1 が担当に戻る（切り戻し）までの時間も記録する

**結果**

| 項目 | 値 |
|---|---|
| 止まり始め | T0 + 4.7秒 |
| 停止時間 | 3秒（失敗 2回） |
| 検知時間 | 1分35秒 |
| 復旧まで | 7.7秒 |
| 戻り方 | VRRP で #2 が自動で担当になった（人の操作なし） |
| 最初の通知 | RouterDown（#1 が応答しない・1分続いたら） |
| VrrpFailover の通知 | T0 + 約5分13秒（#1 が起動してから） |
| 切り戻し | 途切れ0回（以後は自動に変更） |

**考察**：IX #1 の電源を抜いてから 3.0 秒（ping 失敗2回）で #2 が引き継ぎ、インターネットもマイクラも止まらずに済んだ。通知は「#1 が応答しない」（RouterDown）が T0 から約1分35秒で届いた。一方「#2 に切り替わった」（VrrpFailover）は #1 の状態を SNMP で見る作りだったため、#1 の電源が切れている間はデータがなく発報せず、#1 が起動して待機（Backup）と答えた T0+約5分13秒に初めて出た。→ #2 側の状態（#2 が Master か）で判定するようルールを修正した。電源断のときにどれだけ早くなったかは、次の電源断の試験で確かめる。試験時は preempt が2台とも off で、#1 が直っても自動では戻らなかった。手で切り戻すと途切れ0回だったため、#1 だけ preempt を on にして、直ったら自動で戻る設計に変えた

<a id="wan"></a>
### 回線障害（#1 の回線だけ切る）（✅ 合格）

- **目的**：ルーターは動いているが回線だけ切れたとき、watch-group で #2 に切り替わるか
- **計測方法**：failtest.sh（ping 0.5秒ごと＋Alertmanager を2秒ごとに確認）、IX #1 の show vrrp
- **実施日**：2026-11-17 08:57

**試験方法**

1. 前提：#1 が担当（preempt on）、#1 に watch-group WAN1（自分の PPPoE から 1.1.1.1 に届かなければ 7つの VRRP を止める）
2. mon01 で ./failtest.sh ping:1.1.1.1 VrrpFailover を起動
3. Enter（T0）の直後に IX #1 で interface GigaEthernet0.1 → shutdown（回線だけを切る。ルーター本体は動いたまま）
4. 通知が出て計測が終わったら、もう一度 failtest.sh を起動して no shutdown。#1 が自動で担当に戻るか、途切れるかを測る

**結果**

| 項目 | 値 |
|---|---|
| 止まり始め | T0 + 1.0秒 |
| 停止時間 | 13.3秒（失敗 24回） |
| 検知時間 | 1分23秒 |
| 復旧まで | 14.3秒 |
| 戻り方 | watch-group が回線断を見つけて #1 が担当をやめ、#2 が自動で引き継いだ（人の操作なし） |
| 通知 | VrrpFailover（T0 + 約1分23秒） |
| 回線を戻したとき | #1 が自動で取り返し、途切れ0回 |

**考察**：ルーター本体は動いたまま回線だけが切れた場合、VRRP 自体は「#1 は元気」と判断してしまうため、そのままでは切り替わらない。watch-group で #1 自身の回線（1.1.1.1 に届くか）を見張り、届かなくなったら #1 が担当を降りるようにしたことで、13.3 秒で #2 に切り替わった。ルーター障害（3.0 秒）より長いのは、watch-group が「回線が切れた」と判断するまでの時間がかかるため。VrrpFailover は T0 から約1分23秒で届いた（今回は #1 が動いたままなので、#1 に状態を聞けた）。回線を戻すと preempt により #1 が自動で担当に戻り、そのときの途切れは0回だった

### ノード障害（② pve-app の電源を抜く）（未実施）

- **目的**：サーバー1台が突然止まっても、HA で別のサーバーに移ってサービスが戻るか
- **計測方法**：failtest.sh（TCP 0.5秒ごと）、Proxmox の HA 画面・タスクログ

**試験方法**

1. 前提：対象のサービス（例：Forgejo 192.168.20.45:3000）が HA ＋ Ceph に入っていて ② で動いていること
2. 計測は止めないノード上の端末で行う：./failtest.sh tcp:192.168.20.45:3000 NodeDown（AM=http://192.168.20.30:9093）
3. Enter の直後に ② の電源ケーブルを抜く（T0）
4. HA がほかのノードでサービスを起動し、ポートが開くまで待つ
5. ② の電源を戻し、Ceph が HEALTH_OK に戻るまでの時間も記録する

**考察**：② には proxy01（VM 3010：Nginx Proxy Manager・cloudflared）もあり、止めると Web 公開も一時的に止まる。③ を止める場合も vpn01（relay01 からマイクラへの入り口）が移るまで外からのマイクラが切れる。どちらもマイクラに人がいない時間に実施する。git01 と db01 がどちらも ② にあるため、依存関係ごと別ノードで戻るかも確認する

- **目的**：アプリが突然落ちても、人の手なしで自動で立ち上がるか
- **計測方法**：failtest.sh（TCP 0.5秒ごと＋Alertmanager を2秒ごとに確認）

**試験方法**

1. 前提：Forgejo（git01、CT 2045、pve-app）は systemd で動き、Restart=always・2秒後に再起動の設定
2. mon01 で ./failtest.sh tcp:192.168.20.45:3000 ServiceDown を起動
3. Enter（T0）の直後に pve-app で pct exec 2045 -- systemctl kill -s KILL forgejo（プロセスを強制終了）
4. 自動で戻るか、通知が出るかを3分間見る

**結果**

| 項目 | 値 |
|---|---|
| 止まり始め | T0 + 2.1秒 |
| 停止時間 | 2.5秒（失敗 5回） |
| 検知時間 | 通知なし |
| 復旧まで | 4.6秒 |
| 戻り方 | systemd が自動で再起動した（Restart=always）。人の操作なし |
| 通知 | 出なかった（想定どおり） |
| 通知の条件 | 2分続いたら |

**考察**：2.5秒で自動復旧したため、Prometheus（30秒ごとの確認）のグラフにも Uptime Kuma にも止まった跡が残らなかった。通知は「2分続いたら」の条件なので出ていない。すぐ直る落ち方では管理者を呼ばない、という狙いどおりの動き。短い停止は failtest.sh のような細かい計測でしか見えないことも分かった

### サービス停止b（止まったまま → 何分で気づけるか）（✅ 合格）

- **目的**：自動で戻らない止まり方をしたとき、何分で管理者に通知が届くか
- **計測方法**：failtest.sh（TCP 0.5秒ごと＋Alertmanager）、Uptime Kuma の通知時刻（Discord）
- **実施日**：2026-11-16 14:39

**試験方法**

1. mon01 で ./failtest.sh tcp:192.168.20.45:3000 ServiceDown を起動
2. Enter（T0）の直後に pve-app で pct exec 2045 -- systemctl stop forgejo（人が止めた扱いなので自動では戻らない）
3. 通知（Discord）が来たら pct exec 2045 -- systemctl start forgejo で戻す

**結果**

| 項目 | 値 |
|---|---|
| 止まり始め | T0 + 1.5秒 |
| 停止時間 | 47秒（失敗 92回） |
| 検知時間 | 45秒 |
| 復旧まで | 48.5秒 |
| 戻り方 | Uptime Kuma の通知を見て、手で起動（systemctl start forgejo） |

**考察**：自動で戻らない止め方（systemctl stop）では、T0 から約45秒で Uptime Kuma が「git.ch1w4.com が 502 を返す」ことに気づき Discord に通知した。利用者と同じ URL を外側から確認しているので、利用者が困るのとほぼ同時に気づける。Prometheus の ServiceDown は「2分続いたら」なので、それより前に手で戻したため出ていない。監視を2段（URL を見る Kuma／ポートを見る Prometheus）にしているので、片方が遅くてももう片方が先に気づく。「戻った」の通知は Kuma の次の確認（60秒ごと）まで遅れる

### 監視サーバー停止（mon01 を止める）（✅ 合格）

- **目的**：監視そのものが止まったとき、外の監視（mon-ext01）が気づけるか
- **計測方法**：failtest.sh（TCP 0.5秒ごと）と、Uptime Kuma が記録した通知の時刻（mon01 が止まるので Alertmanager は使えない）

4. 通知を見てから ha-manager set ct:2030 --state started で戻し、ポートが開くまで計測する

**結果**

**考察**：mon01 が止まると Prometheus・Alertmanager も止まるため、家の中の監視だけでは気づけない。外（Oracle Cloud の mon-ext01）から見張っているので、T0 から約2分18秒で Discord に通知が届いた。通知までの時間は「60秒ごと・再試行2回」の設定によるもので、一瞬の通信の乱れで誤報を出さないための待ち時間（最大約3分）。通知の時刻は Kuma の記録（14:24:00、分単位）から計算したため、誤差は1分以内。

<a id="power"></a>
### 停電（UPS で安全に止めて、復電で戻る）（計画中）

- **目的**：停電でも壊さずに止まり、電気が戻ったら人の手なしで全部戻るか
- **計測方法**：ストップウォッチ、Proxmox のタスクログ、この画面の記録

**試験方法**

1. UPS と NUT を入れてから行う
2. UPS の電源プラグを抜く（T0）→ 決めた残り時間でサーバーが順に自動停止するか
3. プラグを戻す → BIOS の自動起動 → Ceph → HA → 各サービスが戻るまでの時間を測る

**考察**：UPS 導入後に実施
